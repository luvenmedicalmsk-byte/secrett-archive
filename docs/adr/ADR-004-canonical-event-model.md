# ADR-004 — Каноническая модель события / процесса / причинного графа

**Статус:** Approved · **Дата:** 2026 (финализирован в рамках ADR-серии)

## Контекст

Корень ошибок классификации: у системы не было единой канонической модели события.
Каждый этап пайплайна (домен-роутинг, severity, гео, кластеризация процессов, causal-граф)
пере-выводил смысл события собственным набором regex. Одно и то же событие получало
разный «смысл» на разных этапах → рассогласования (военный удар в economy, торнадо как
«ударил по», климатическое следствие военного удара помечалось как климатическая природа).

## Решение

Ввести **единую каноническую модель** и явный порядок этапов её вычисления:

**Порядок: B → C → A1 → A2**
- **B (Base / событие)** — атомарное событие с каноническими полями (тип, домен, феномен,
  origin, атомарность). Смысл выводится один раз, не пере-выводится ниже по потоку.
- **C (Causal / причинность)** — связи между событиями (causes / caused_by / related).
- **A1 (Aggregation L1)** — кластеризация событий в процессы (identity, first_seen, timeline).
- **A2 (Aggregation L2)** — макро-слой, связность, pressure.

**Дисциплина внедрения:** каждый этап миграции = аудит-отчёт + явное утверждение
пользователем перед переходом к следующему. Ни один этап не пере-выводит географию,
домен или тип, если они уже установлены каноном (NO RECALCULATION).

## Следствия

- Канон-реестр (`_CANON_TYPE`) развивается **отдельно** от legacy (`_PROC_TYPE`); домен
  следует за каноническим типом, а не наследует legacy.
- Появляется база для ADR-006 (Coverage), ADR-008 (Signal Purity), ADR-009 (Lifecycle).
- Порядок B→C→A1→A2 — обязателен; нарушение порядка возвращает проблему пере-вывода смысла.
